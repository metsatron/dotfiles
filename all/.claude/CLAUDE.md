## Output formatting

**Never hard-wrap prose.** When writing or editing any markdown — notes, reports, comments, documentation, file bodies — write each paragraph, bullet, and list item as ONE single unbroken line and let it soft-wrap. Never insert manual newlines to wrap text at a column width. Hard-wrapped prose forces a wasteful wholesale file regeneration whenever it later has to be reflowed; single-line paragraphs never do. Only code blocks, tables, YAML frontmatter, and config keep their structural line breaks.

## Debugging discipline — environment claims (sealed 2026-07-09)

Your tool subprocess is not the user's shell. Its environment differs — Claude Code scrubs `NO_COLOR` from its subprocesses, among others — so never answer "is X set in the environment?" by running `env` in your own Bash tool. You will be reading a different process and will confidently report the opposite of the truth. Have the user check in the affected shell, or read the specific live PID, filtered to the exact variable names needed — never a broad `/proc/<pid>/environ` dump.

- **A disagreement between your reading and the user's IS the finding.** If your `TERM`/`SHELL`/`COLORTERM` differs from theirs, stop and reconcile it. Never note the mismatch and reason past it — that is how a live `NO_COLOR=1` got misreported as unset and cost two days.
- **Where a variable is declared is not where it is observed.** Grepping config trees proves nothing about a running session; a variable injected at runtime is declared nowhere on disk.
- **`bash --norc` / `--noprofile` isolate rc files, not the environment.** An "isolated" shell still inherits every exported variable from its parent, so an environmental hypothesis tested that way has no control at all. Use `env -i`, or explicitly unset the suspect variable.
- **Never assert an environment fact to a third party** — bug report, issue, outbound message — unless you observed it in the user's actual shell. Software has been called buggy for obeying a variable the agent never looked for.

## Verification discipline (sealed 2026-07-14, the sanctuary Doom hunt)

Nine defects stacked on each other, and seven were invisible until the one above was cleared. Green builds, clean exits, and a menu that generated perfectly all lied in sequence. What follows are the traps that cost real time.

- **The metric is never the evidence.** A tool you write to detect a failure can *produce* that failure — and it will do so with a confident summary. Three times in one session: a report tool truncated its subject's output at 40 lines and declared WADs "DROPPED" that had loaded fine; a fuzzy matcher's own containment rule forced its own confidence score to 0.93, "matching" `Blood Machines Theme` to `theme.ogg` and `PONPON SHIT` to `d.mp3`; a grep for a libretro core "found" `prboom` because RetroArch ships an `.info` metadata stub for every core that has ever existed, while only the `.so` is real. **Before trusting a detector's verdict, validate the detector against ground truth you obtained another way — and read its raw output, not its summary.** A 100% hit rate is a reason for suspicion, not celebration.
- **Verification must not be indistinguishable from use.** An inspection sweep ran the real engine 53 times and seized the user's live desktop, cycling through his entire game library, grabbing audio each time — while he sat in front of it. A tool whose only job is to READ has no business opening a window, playing audio, or taking a lock. Force headless (dummy video/audio drivers, `-nodraw`-style flags), and say so in the source so nobody removes it. Never run a sweep against a session a human is using.
- **A green build proves the thing was built, never that it is reachable.** Engines compiled and installed while the shim had no `case` branch to route them; a core landed in `lib/retroarch/cores/` while every consumer looked in `lib/libretro/`. Exit 0 said nothing. Only a dry-run of the real call path found it. **Verify the consumer, not the artifact.**
- **Verify where the code RUNS, not where it is convenient.** A menu generator was "verified" on the host — where `$HOME` and `PATH` differ from the container it actually executes in — and shipped broken twice. Host-only verification of in-guest behaviour is worthless. Label every claim with where it was checked.
- **Search for the capability, not the shape the incumbent assumed.** Doom's core was built from a dead upstream at the bottom rung of the sourcing ladder because the search was for a *libretro core* (none exists) — while the maintained standalone *engine* sat in Guix main at rung 1 the whole time. When a search comes back empty, ask whether the search term encoded someone else's architecture.
- **A command that FAILED produces empty output, and empty output passes a count check.** `git -C <relative-path> …` failed with *"No such file or directory"* — the Bash tool's working directory had silently persisted from a `cd` in an earlier call — and the `grep -c` piped after it dutifully printed `0`, which was read as "0 files clobbered, restore succeeded". The restore had never run. **Check exit status, not just output**; a guard that reports success from a dead pipeline is worse than no guard. And remember the shell's cwd persists across tool calls: a relative path is not the same path it was two commands ago.
- **Absence found by your own search is not absence.** "There is no Winamp art anywhere on this machine" was asserted from a `find` scoped to the wrong roots, then from a `grep` whose match was real but sorted below a `head -40` cutoff. The art was in the repo the whole time, and the user had to point at it. Before reporting that something does not exist, re-run the search from a different angle — different root, different tool, no truncation — and say where you looked. A truncated or mis-scoped search is a detector, and detectors lie.
- **Do not build a theory on your own reading of a low-resolution screenshot.** Two consecutive misidentifications of 16px toolbar buttons produced a confident, entirely wrong root cause. When the evidence is visual and small, construct a controlled experiment with known-good markers (render known icons as separators and count the gaps) instead of squinting harder.
