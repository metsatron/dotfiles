* Galaxy S24 Ultra — Phone Satellite README

The operational book for the phone: what runs on it, what heals it, and the parts that live in app UIs and can never be tangled. The DECLARATIVE half — every package, script, and config — lives in =package-termux.org= and deploys via its apply scripts; this document carries the NON-declarative half (Tasker rules, app toggles, boot behavior) plus the map between them. Stood up 2026-08-17, the escape-velocity climb.

** Architecture in one breath

Termux is the sovereign host (Bionic userland, sshd, runit supervision, pulseaudio, herdr). Inside it, a Debian proot enclave carries the glibc world: Claude Code and the kitten TTS venv. HelmCortex is NOT mounted here — the phone talks to the fleet over ssh, and DotCortex deploys via git pull + stow.

** The immune system (four layers, all proven live 2026-08-17)

- *Reboot* → Termux:Boot runs =~/.termux/boot/00-services= (wake lock, then termux-services' own starter): sshd, pulseaudio, herdr come up supervised without the app ever being opened. Proven: 58-second power-cycle to fully reachable.
- *App death* → Tasker heartbeat resurrects the Termux service within 5 minutes (see the Tasker chapter). Proven: killed 20:12:16, self-healed 20:15:06, unattended.
- *System culling* → the Android phantom process killer is DEFUSED (=termux-defuse-apply= via Shizuku/rish: monitor off, process ceiling maxed, sync-disable persistent). On this build the defusal SURVIVES reboots. Verify anytime with =termux-defuse-check=.
- *Doze* → wake locks are held by the boot script for supervision and by the voice pipeline for renders and playback.

** Boot ritual (current state)

Zero taps for the core: supervision, sshd, and the tailnet (Always-on VPN) come up by themselves. Shizuku is the one holdout — its ADB-mode service start is the lane Android actively fights; the Tasker boot rule force-enables wireless debugging and launches the app, but the SERVICE may still need a tap on Shizuku's notification (and note: opening the Shizuku APP is not the same as its service RUNNING — =rish -c id= answering is the only proof). Shizuku is only needed for re-running the defusal after OS updates and for permission grants, not for daily operation.

** Tasker rules (built in the Tasker UI — cannot be tangled, rebuild by hand from here)

Tasker holds two permissions granted via rish that it cannot request itself: =com.termux.permission.RUN_COMMAND= and =android.permission.WRITE_SECURE_SETTINGS=. Re-grant after a Tasker reinstall: =rish -c "pm grant net.dinglisch.android.taskerm <permission>"=.

- *Task "Termux Revive"*: one action — Plugin → *Termux:Tasker* (the official plugin app from F-Droid, must match Termux's F-Droid build) with Executable =termux-revive= (resolves to =~/.termux/tasker/termux-revive=, deployed by stow from the org), terminal/stdin options unchecked so it runs in the background. Do NOT build this with a raw System → Send Intent: Tasker sends intent extras as strings while Termux reads =RUN_COMMAND_BACKGROUND= as a boolean, so the background flag is silently ignored and every heartbeat opens a terminal session that steals the screen (bitten live 2026-08-17). Requires =allow-external-apps=true= in termux.properties and the RUN_COMMAND grant (both already handled).
- *Profile "Termux Heartbeat"*: Time, From/To empty, Repeat every 5 minutes → runs Termux Revive. The revive is idempotent (the boot script no-ops when supervision is already up), so firing it blind is safe. The Task also serves as a manual instant-resurrect button.
- *Shizuku boot assist — SHELVED* (2026-08-17): the Custom Setting action errored on this build despite the WRITE_SECURE_SETTINGS grant, and the fight is not worth the prize — the defusal persists across reboots without Shizuku, so the service is only needed for occasional re-grants and re-applies. The two-tap habit (open Shizuku, start via wireless debugging) stands. Ground truth for "is Shizuku running": =rish -c id= answers — the app's status label is not the service.

** App-level toggles (Settings app, by hand)

- Battery → *Unrestricted* for: Termux, Termux:Boot, Shizuku, Tasker. A battery-frozen Shizuku binder times out every rish call.
- VPN → Tailscale → gear → *Always-on VPN*. Android allows exactly ONE active VPN: AdAway (local-VPN ad blocking) and Tailscale are mutually exclusive — Tailscale won that seat. Ad blocking moves to the DNS layer (below).
- Storage permission for Termux (=termux-setup-storage=) — needed for the rish export copy and any shared-storage work.

** Tailscale, plainly

By default Tailscale routes ONLY tailnet addresses through the tunnel; normal internet traffic leaves the phone directly. To route EVERYTHING through home while on the road, advertise a fleet machine as an *exit node* and select it on the phone — then all traffic tunnels home first. For ad blocking without AdAway's VPN seat: run a DNS filter (AdGuard Home / Pi-hole class) on a fleet machine and set it as the tailnet's global DNS in the admin console — every device on the tailnet gets filtered DNS everywhere, no VPN conflict, no exit-node bandwidth cost. (Standing candidate project; not yet deployed.)

** Voice lane (summary — full story in package-termux.org)

Consort replies render ON the phone: the fleet hook resolves voice and speed from pvox config, cleans the text, and ships it to =termux-kitten-say=, which streams sentence-by-sentence through the fp32 kitten nano (int8 measured SLOWER on ARM — RTF 0.95 vs 0.64) into pulseaudio. Truth logs: fleet side =~/.cache/pvox-reply.log= (kikin), phone side =~/.cache/kitten-say.log=. Fallback when the phone is unreachable: fleet-rendered WAV shipped to the fallback speaker.

** The phone as a literate machine (2026-08-17, late)

GNU Emacs 30.2 is in the manifest, and =tangle-one= (stowed from DotCortex like everywhere else) runs on the phone natively — first run reproduced kikin's tangle output byte-identically (it even caught a tangled artifact kikin had forgotten to commit, by regenerating it exactly). So the phone can edit AND tangle its own org sources: =emacs package-termux.org= → edit → =tangle-one package-termux.org= → run the relevant apply script. Discipline is the same as on any tangle machine: commit the org and its tangled artifacts together (pathspec), never edit tangled output directly, pull before editing. The kikin-tangles-git-carries chain remains the default; local tangling is for working ON the phone's own chapter from the phone itself.

** Recovery cookbook

- Phone silent, replies missing → check =~/.cache/kitten-say.log= on the phone and =~/.cache/pvox-reply.log= on the hook machine; every render/skip/failure writes one line.
- Services down after an app kill → wait out the heartbeat (≤5 min), tap Termux Revive in Tasker, or just open Termux once.
- Enclave venv wounded (interrupted install: broken dist-info, torch reappearing) → =proot-distro login debian -- bash -lc "rm -rf ~/kitten-venv"= then =termux-kitten-apply=; the no-torch assertion gates the result.
- Defusal state unknown (after an OS update) → =termux-defuse-check=; re-apply with =termux-defuse-apply= (needs Shizuku running).
- Everything from bare metal → =termux-pkg-apply=, =termux-services-apply=, =termux-enclave-apply=, =termux-kitten-apply=, =termux-rish-apply=, =termux-defuse-apply=, in that order, all from the stowed DotCortex checkout.
